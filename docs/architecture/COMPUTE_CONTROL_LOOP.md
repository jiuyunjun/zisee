# Compute-for-Quality 控制环重构设计

状态：2026-09-11 设计定稿，按第 6 节分步实现。上位设计见 [Compute-for-Quality](Compute-for-Quality.md)，进度见 [handoff](../development/COMPUTE_QUALITY_HANDOFF.md)。

## 1. 为什么重做

nezha 真机四通电话（`2d68091`…`d121c2d`）里 front 始终在 C0/C1 之间振荡，从未到过 C2，ROI 从未在真机运行。数据：

| 版本 | 处理尺寸 | 总 P95 | 自身 GPU（timer） | 同步等待 |
|---|---|---|---|---|
| 两次 glFinish | 1080p | 7.9ms | 1.7ms | 大部分在池内 glFinish |
| 单次 glFinish | 540p | 5.3ms | 1.4ms | fin95 3.0ms |
| 单次 glFinish | 720p | 7.8ms | 2.6ms | fin95 3.7ms |

降噪 shader 本身远低于 5ms，超出部分来自同步与读回。问题不在阈值，而在控制环：

1. **盲目恢复**：超标 → 冷却 → 策略 C0 → 不处理 → 25s「稳定」→ C1 满负载 → 再超标。C0 下没有处理样本，稳定不能证明处理链可恢复。
2. **压力类型混为 LOAD**：处理器冷却/锁死、编码耗时、处理 P95 全部变成 `cpuLimited → C0 LOAD`，而 GPU 同步、读回、编码器、热需要完全不同的动作。
3. **测量口径错误**：预算用「相机线程发起 → glFinish 返回」的总时长，包含线程调度、提交、等 GPU 空闲、读回，却被解释为「增强算法耗时」。q/cpu/fin/gpu 已拆分，但只进日志不进决策。
4. **每帧 CPU↔GPU 屏障**：同步 glFinish 让相机线程等待 GPU 完成，GPU 流水线失去异步性。
5. **辅助读回污染主统计**：2Hz 场景读回（以及 C2+ 的 ROI 读回）是同步 `glReadPixels`，在 60 帧窗口里恰好落在 P95 附近。
6. **单帧 >20ms 即暂停 30s**：偶发抖动（调度、GC、驱动、调频）惩罚过重。
7. **指数退避 30/60/120s → 锁死**：GPU 负载是连续变化状态，不是网络重试。
8. **等级与功能捆绑**：ROI 只能在 C2+ 启用，没有成本依据。
9. **前后摄各算各的**：共享同一 GPU、带宽、热包络，却各有 5ms 预算。

更正第 10 点：`>1080p 旁路` 检查的是 WebRTC 按发送规格 adapt 后的 buffer 尺寸，处理也在该尺寸进行，不是按传感器源分辨率禁用。

## 2. 目标结构

```text
Thermal / Battery / Encoder ──► GlobalComputeGovernor（设备总预算，热/电/编码只在这里）
                                      │ 按主/辅分配
                          ┌───────────┴───────────┐
                     front budget             back budget
                          │                       │
                  FeatureScheduler（NR 强度、分析频率、ROI 频率、处理分辨率独立调度）
                          │
                  CameraQualityProcessor（逐帧执行 + 本地保护状态机，唯一解释处理健康度）
```

原则：

- **单一解释权**：处理健康度只由处理器的本地状态机判断；策略/调度器不再把处理器状态当作 CPU 负载反馈回 C0，消除「策略不让跑 → 没样本 → 策略无法确认」的死循环。
- **降级快、恢复有探测**：恢复必须基于真实处理样本。
- **按压力类型动作**，不统一降到 C0。

## 3. 指标（第 1 步）

每个处理帧只统计主处理链（缩放 + 降噪），辅助任务单独统计：

| 指标 | 定义 | 用途 |
|---|---|---|
| `baseGpu` | GPU timer query 包住缩放+降噪 | 算法自身成本；timer 不可用为未知 |
| `submit` | GL 线程开始执行到提交完成 | CPU/驱动提交成本 |
| `wait` | 提交完成到 GPU 完成（当前为 glFinish） | 同步/争用 |
| `queue` | 相机线程发起到 GL 线程开始 | 线程调度 |
| `added` | 进入处理器到输出交付下游 | 端到端额外延迟（用户可感知） |
| `aux` | 场景分析 / ROI 取样各自耗时 | 辅助任务成本，不进主统计 |

- 窗口：最近 120 个处理帧（约 4s），输出 P50/P95。预热、尺寸切换帧不进窗口。
- 周期日志 `RTC_COMPUTE_STATS`（≤ 每 10s 一行），无论是否超标都有真机数据。
- 辅助任务移出主帧关键路径：作为 GL 线程上主帧之后的独立任务执行；若期间已有新帧写入其依赖的历史纹理则跳过。ES3 下后续可改 PBO + fence 异步读回。

## 4. 本地保护状态机（第 2 步）

取代冷却/锁死/退避三件套：

```text
          violation                    violation at lowest tier
NORMAL ─────────────► DEGRADED(tier−1) ─────────────────────────► PROBE
  ▲                        │ 稳定 10s → tier+1                    │ 30 个健康样本 → DEGRADED(最低处理档)
  └────────────────────────┘                                      │ 不健康 → 继续 PROBE（不锁死）
HARD_DISABLED：仅 GPU 异常 / 初始化失败
```

- **工作档（由重到轻）**：`FULL`（缩放+降噪+辅助）→ `NO_AUX`（缩放+降噪）→ `RESIZE_ONLY` → `OFF`。每次违规降一档，立即生效；同一档稳定 10s 升一档。
- **PROBE**：`OFF` 档下每 10 帧对 1 帧做「影子处理」——跑最轻处理链并计时，但仍交付原帧，因此不会出现增强/未增强交替闪烁；采满 30 个样本且健康则回到 `RESIZE_ONLY`。探测持续进行，不指数退避、不锁死。
- **证据连续性**：停采/切摄/AR 所有权变化、外部 C0 旁路、处理尺寸变化、采样时钟倒退或处理样本间隔超过 3 秒时，清空健康窗口和恢复计时，保留当前工作档、失败次数及 HARD_DISABLED。OFF 的常规九帧旁路不清空探测证据；停采时间不能用于升档或消除历史失败。
- **违规判定（deadline miss rate，替代单帧 20ms）**：窗口内
  - `baseGpu` P95 > 5ms（算法过重），或
  - `added` > 12ms 的帧占比 > 5%，或
  - `added` > 20ms 的帧在 5s 内 ≥ 3 帧，或连续 3 帧 > 12ms。
  单个长帧只记录不惩罚。阈值为工程初值，第 5 步用真机数据标定。
- **压力分类**上报（诊断 + 调度依据）：处理器侧 `NONE / GPU_COMPUTE / GPU_SYNC / CPU_SUBMIT / QUEUE`（`QUEUE` 含辅助读回占用 GL 线程与线程调度）；`ENCODER / THERMAL` 由策略的 LOAD/THERMAL 原因表达，不再混入处理器健康度。`GPU_COMPUTE` 降处理强度/分辨率；`GPU_SYNC` 优先由第 3 步流水线解决，期间降档而不是关闭全部；`QUEUE` 由 FULL→NO_AUX 先去掉辅助任务。当前实现统一每次违规降一档，按压力选择不同动作留待第 4 步调度器。

## 5. 异步流水线（第 3 步）

去掉每帧阻塞相机线程的 glFinish；同步只能换位置，不能消失（下游编码器/渲染在其他 EGL context 读取纹理，WebRTC `TextureBufferImpl` 不携带 fence）：

- 输入：缩放（唯一读取 OES 输入的 pass）后插 fence；fence 触发后才 release 输入帧，相机才能回收纹理。
- 输出：降噪后插 fence；GL 线程在 fence 触发后按序交付下游。在途 ≤ 2 帧，积压则丢弃最旧待交付帧（不排队）。
- `added` 此后等于 fence 触发延迟；GPU 争用仍会反映在其中，但不再阻塞相机线程，也不再混入算法成本。
- **前置核对**：用 javap 确认 WebRTC 144.7559.15 中 `VideoSource` 对 processor sink 的线程约定（能否在 GL 线程回调）、`EGL_KHR_fence_sync`/`glFenceSync` 可用性；不满足则保留同步交付，只做输入早释放。

## 6. 实施顺序

| 步骤 | 内容 | 验收 |
|---|---|---|
| 1 | 第 3 节指标 + 辅助任务移出主路径 + 周期统计日志；决策逻辑暂不变（但只统计主处理链） | 单测；模拟器；真机日志给出 baseGpu/added/aux 分布 |
| 2 | 第 4 节状态机，移除冷却/退避/锁死与 `cpuLimited` 反馈；ROI 与 C2 解绑，改由工作档与自身成本决定 | 单测覆盖所有迁移；真机不再长时间 C0 且无增强/原帧闪烁 |
| 3 | 第 5 节异步流水线 | 前置核对通过后实现；added/相机阻塞时间对比 |
| 4 | GlobalComputeGovernor：双摄共享总预算（初值主 5ms、辅 3ms 的 baseGpu），功能独立调度 | 双摄真机 |
| 5 | 用真机数据重新标定所有阈值 | 记录依据 |

每步：JVM 单测、Debug/AndroidTest/lint/Release 编译、模拟器 instrumentation，更新 handoff 后 commit + push。
